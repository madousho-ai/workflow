# plan-arch

本 Skill 定义一系列跟用户探讨，目的对齐，最后给出完整方案的流程

## When to use

以下任意情况触发:
- 用户想进行大范围更改，横跨多个代码模块
- 用户试图创建新的功能模块 (ex. 实现协议库/新事务)
- 在项目早期规划阶段

## Definition

### 讨论流程
- 新需求
- 需求共识
- 架构研究
- 架构共识

#### 子流程

##### 新需求  
当用户提出一个新的需求(跨出当前讨论主题)时切换到此状态。  
1. 进行 [用户需求对齐] 章节的内容
2. 进行 [了解项目] 章节的内容
3. 跟用户多轮对话，进行多次步骤 1-2
4. 当用户口头同意后切换到 需求共识

##### 需求共识
1. 在 锚点文件 对应的需求的[描述]章节写入/更新为当前共识内容
- 只写入到节点的描述，不要创建子节点
2. 切换到 架构研究

##### 架构研究
1. 根据用户需求 提取关键词，启动 subagent 联网搜索
- 搜索不限于文档，别人的实现，其他项目
- 抽象其他人的设计模式
2. 搜索完成后展示给用户
3. 继续跟用户讨论，如果用户修改了需求，按照 [新需求] 的步骤跟用户达成共识，更新锚点文件之后判断相应更新
4. 用户显式确认架构后，进入 架构共识

##### 架构共识
1. 在 锚点文件 对应的需求的[架构]章节写入/更新为当前共识内容
2. 等待用户提出新的需求后，进入 新需求

### 锚点文件
docs/arch 中的一个 markdown 文件
格式为:

```markdown
# 树 Root (总需求)

[一些描述信息]

## 树节点1 (子需求 [需求名字/标题])

### 描述

### 架构

...可能的多个树节点...
```

### 架构树
一个大任务可以被拆分成多个模块

## 规则

### 行动
在尝试推进到下一步之前，永远需要用户的许可 (用户必须说 "进行下一步")。
```markdown
## Assistan
下一步
在我把以上内容写入锚点文件的 ## 架构 章节之前，有两个点想确认：
1. xxx
2. yyy

## 用户
针对1和2 提出了一些意见
```
注意此时不代表用户批准你修改后的方案，需要显式许可才能继续。

## Instructions

### 情况1: 新会话(初始架构讨论)

1. 初始化文档
- 简单抽象用户需求到一个短的英文标题
- 在 docs/arch 中以这个标题创建一个 markdown 文件
- 这个文件即为 锚点文件
2. 为用户初始需求迭代一轮 讨论流程
3. 在用户允许后，画出架构树
4. 等待用户开新的会话，为每一个树节点做决策

### 情况2: 用户针对架构树的一个节点进行讨论
1. 迭代 讨论流程
2. 用户许可后更新 锚点文件 对应的节点

### 用户需求对齐

1. 换一种方式(Paraphrase) 复述用户需求
2. 给出具体例子(尽量不要写代码 要写的话也是写简要的pesudo-code)

### 了解项目

1. 阅读项目 ADR 文档记录 (docs/adr)
